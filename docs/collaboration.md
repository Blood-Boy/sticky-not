# التعاون على المجلدات والنوتس (Collaboration)

> **الحالة: قيد التنفيذ.** الكود لسه مش في `main`. الملف ده بيوصف التصميم اللي اتبنى عليه، وبيتحدّث لما الفيتشر يتدمج.

## الفكرة

أي يوزر يقدر يشارك **نوت واحدة** أو **مجلد كامل** مع يوزر تاني، والاتنين يعدّلوا عليها مع بعض:

1. أنا أدوّر على اليوزر بالاسم وأبعتله طلب.
2. الطلب بيوصله في **الإشعارات**. لو قبل، المجلد أو النوت بتنزل عنده.
3. بعد القبول الاتنين بيشوفوا نفس المحتوى، وتعديل أي واحد فيهم بيظهر عند التاني.

```
المالك ──ابعت طلب──▶ pending ──قبول──▶ accepted ──▶ الاتنين بيعدّلوا
                          └───رفض──▶ declined ──(المالك يقدر يبعت تاني)
```

## الصلاحيات

فيه دورين بس:

| | المالك (owner) | المشارك (editor) |
|---|:---:|:---:|
| يقرأ ويعدّل العنوان واللون والسطور | ✅ | ✅ |
| يضيف نوت جوه مجلد مشارَك | ✅ | ✅ |
| يحذف نوت أو مجلد | ✅ | ❌ |
| ينقل نوت أو يغيّر اسم المجلد | ✅ | ❌ |
| يبعت طلبات ويشيل أشخاص | ✅ | ❌ |
| يخرج من المشاركة | — | ✅ |

مشاركة **مجلد** بتدّي الوصول لكل النوتس اللي جواه، بما فيها اللي تتضاف بعد كده. النوت دايماً بتفضل ملك صاحبها الأصلي حتى لو اتعدّلت من حد تاني.

## قاعدة البيانات

الجداول الجديدة في `supabase/schema.sql`، والـ RLS مفعّل عليها من غير policies زي باقي الجداول، لأن السيرفر هو الوحيد اللي بيكلم Supabase.

- **`shares`**: صف لكل طلب.
  - `owner_id` و`invitee_id`: صاحب الشيء والمدعو.
  - `note_id` أو `folder_id`: واحد منهم بالظبط (constraint).
  - `status`: `pending` أو `accepted` أو `declined`.
  - مفيش طلبين لنفس المدعو على نفس النوت أو المجلد (unique index)، والمالك مايقدرش يدعو نفسه.
  - حذف النوت أو المجلد بيحذف طلباتها (`on delete cascade`).
- **`notes.version`**: رقم بيزيد مع كل حفظ، وبيتستخدم في منع تضارب التعديلات.
- **`notes.updated_by`**: آخر واحد حفظ، عشان يتعرض للمشارك الآخر.

## الـ API

كل المسارات محتاجة تسجيل دخول، وموجودة في `server/workspace.js`.

| المسار | الوظيفة |
|---|---|
| `GET /api/users/search?q=` | بحث عن يوزر بأول حروف اسمه. أقل حاجة حرفين، وبيرجّع 8 نتايج على الأكتر، من غير اليوزر نفسه. |
| `POST /api/shares` | المالك يبعت طلب: `{ note \| folder, username }`. |
| `GET /api/shares?note=\|folder=` | الناس على النوت أو المجلد (المشارك بيشوف اللي قبلوا بس). |
| `DELETE /api/shares/:id` | المالك يشيل أو يلغي طلب، أو المشارك يخرج. |
| `GET /api/inbox` | الطلبات المعلّقة اللي جاية لي. |
| `POST /api/shares/:id/respond` | قبول أو رفض: `{ accept: true \| false }`. |
| `GET /api/sync` | استعلام خفيف للتحديث (تحت). |
| `PUT /api/notes/:id` | الحفظ بعمليات (تحت). |

### الأمان

السيرفر بيشتغل بمفتاح `service_role` اللي بيتجاوز الـ RLS، فالحماية كلها في الكود:

- كل مسار بيمر على `noteAccess()` أو `folderAccess()` اللي بترجّع `owner` أو `editor` أو `null`. اليوزر مايوصلش غير لحاجته أو لحاجة اتشاركت معاه وقبلها.
- لو اليوزر مالوش وصول خالص للحاجة الرد `404`، عشان مايتعرفش إن الـ id موجود. ولو له وصول بس مش مالك (حذف أو نقل أو دعوة) الرد `403`.
- المالك بس هو اللي يبعت طلبات، وأقصى عدد طلبات معلّقة لليوزر 50.
- البحث بيرجّع الاسم والصورة بس، ومحدود بـ 8 نتايج.

## التعديل المتزامن

لو اتنين فتحوا نفس النوت، إرسال النوت كلها كل مرة معناه إن آخر واحد يحفظ يمسح تعديل التاني. عشان كده العميل بيبعت **عمليات** على مستوى السطر (block) مش النوت كاملة:

```
{ op: "set", block: { id, k?, t?, d? }, after? }   // تعديل سطر أو إضافته بعد سطر
{ op: "del", id }                                    // حذف سطر
```

- لو الاتنين عدّلوا **سطرين مختلفين**، تعديلاتهم الاتنين بتفضل.
- لو عدّلوا **نفس السطر**، آخر حفظ بيكسب في السطر ده بس.
- لو حد عدّل سطر والتاني كان حذفه، التعديل بيتتجاهل والسطر ما بيرجعش.
- الحفظ بيتم بـ `version`: السيرفر بيطبّق العمليات على آخر نسخة ويحاول لحد 6 مرات، ولو فشل يرد `409 busy`.
- منطق الدمج موجود نسختين متطابقتين: `server/merge.js` و`src/merge.js`، واختبار واحد بيقارنهم على عمليات عشوائية.

## التحديث عند التاني

مفيش websockets، لأن الـ API شغال كـ serverless function على Vercel. بدلها **polling**:

- كل **6 ثواني**، و**3 ثواني** لما نوت مشاركة تكون مفتوحة. بيتوقف لما التاب مخفي، وبيتحدّث فوراً لما ترجع له.
- `GET /api/sync` بيرجّع عدد الطلبات المعلّقة وقايمة المجلدات و`version` كل نوت أقدر أوصلها. العميل بينزّل بس النوتس اللي الـ version بتاعها اتغيّر.
- الحفظ بيستنى وقفة 0.5 ثانية في الكتابة، وبيتفرّغ فوراً لما التاب يتخبّى.

## الواجهة

كل الأزرار أيقونات زي باقي التطبيق:

- **زرار مشاركة** على النوت وعلى المجلد، بيفتح نافذة فيها خانة بحث عن يوزر، ونتايج بزرار إرسال الطلب، وقايمة الناس الحاليين مع زرار الشيل أو الخروج.
- **أيقونة الإشعارات** في الهيدر عليها عدّاد، بتفتح الطلبات الجاية مع زراري قبول ورفض.
- الرئيسية بتفصل بتاعتي عن اللي اتشاركت معايا، وعلى كل حاجة مشاركة اسم صاحبها. جوه النوت بيظهر آخر واحد عدّل عليها.

الكود في `src/collab.jsx` (نافذة المشاركة والإشعارات) و`src/Shell.jsx` (الحفظ والـ polling).

## الاختبار

`node --test server/merge.test.js` بيشغّل 15 اختبار على الدمج بدون ما يحتاج `npm install`: تعديل سطرين مختلفين، تعديل نفس السطر، إدخال متزامن، سطر اتحذف، تطابق نسخة المتصفح مع السيرفر، ورفض العمليات غير الصالحة.

**لسه مش متجرّب:** مسارات الـ API والواجهة مع قاعدة بيانات حقيقية. محتاج تجربة يدوية بحسابين:

- [ ] ابعت طلب نوت لحساب تاني، وتأكد إنه بيوصل في الإشعارات.
- [ ] اقبل، وتأكد إن النوت بتظهر عنده بعلامة المشاركة.
- [ ] عدّل سطرين مختلفين من الحسابين في نفس الوقت، وتأكد إن الاتنين بيفضلوا.
- [ ] شارك مجلد، وأضف جواه نوت من الحساب التاني، وتأكد إن المالك بيشوفها.
- [ ] المشارك يحاول يحذف أو ينقل أو يشارك، وتأكد إنه بيترفض.
- [ ] المشارك يخرج، وتأكد إن النوت اختفت عنده وفضلت عند المالك.
- [ ] ارفض طلب ثم ابعته تاني، وتأكد إنه بيرجع `pending`.

## قرارات محتاجة رأي

- **حذف المشارك:** حالياً المشارك مايقدرش يحذف، حتى نوت أضافها هو في مجلد مشارك (النوت دي بتتحسب على صاحب المجلد). ممكن نسمح له يحذف اللي أضافه بنفسه.
- **صلاحية قراءة فقط:** مفيش دور `viewer`. لو عاوزين مشاركة للعرض بس لازم نضيف عمود `role` على `shares`.
- **إشعارات النشاط:** الإشعارات دلوقتي للطلبات بس. مفيش إشعار لما حد يقبل أو يرفض أو يعدّل.
- **Realtime:** لو الـ polling بقى بطيء ممكن ننقل لـ Supabase Realtime، بس ده محتاج تغيير طريقة الدخول لـ Supabase Auth لأن الدخول الحالي بـ JWT خاص بينا.
